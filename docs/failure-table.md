# Failure table: the bonus store

What goes wrong, what the system does, and which test proves it. Test names are the names in
`test/store.test.ts`. "Not tested" means nobody ran it.

| What goes wrong | What the system does | Proved by |
|---|---|---|
| The player sends the same redemption twice, one after the other | The second call returns the first redemption with 200 and changes nothing, even if the body names another item. | `3. the same Idempotency-Key twice: 201 then 200, one redemption, charged once; a new key is a new redemption` |
| The player sends the same redemption ten times at once | One request creates it, the other nine get the same redemption; one grant, coins taken once. | `4. ten identical requests at once: one redemption id in every answer, one grant, charged once` |
| The player does not have enough coins | The ledger refuses the reserve, the redemption ends `insufficient`, and the platform is never called. | `5. not enough coins: insufficient, nothing reserved, the platform is never called` |
| Eight requests at once for a balance that pays five | Exactly five are issued and three are `insufficient`; the balance ends at zero, never below. | `6. eight requests at once for a balance that pays five: five issued, three insufficient, never below zero` |
| The platform refuses the reward (A: 422, B: DECLINED callback) | The redemption ends `refused` with the reason, and the reserve is released so the coins are back in full. | `7a. platform A refuses: refused with the reason, coins back in full, settled`, `7b. platform B declines by callback: refused, coins back in full, settled` |
| Platform A grants but the answer is lost | The redemption stays `submitting`; the next run looks first, finds the grant, and settles; the platform has one grant and one request. | `8. A, lost answer: the grant exists, we are told nothing; the look finds it; still one grant` |
| Platform A never gets the request (lost request) | The redemption stays `submitting`; the next run looks, finds nothing, issues once. | `9. A, lost request: no grant yet; the look finds nothing; then it is issued; one grant` |
| Platform A answers slower than our time limit | The call is cancelled at the limit, the request returns `submitting` in time, and the next run finds the grant. | `10. A, answer slower than the time limit: the request returns in time, recovery gives one grant` |
| Platform B accepts the grant but the answer is lost (B has no idempotency key) | The next run looks before it issues, sees the accepted request, and does not send a second one. | `11. B, lost answer (B has no idempotency): recovery looks first, so only one request exists` |
| Platform B's callback is lost | The redemption stays `submitting` and the periodic look sees GRANTED and finishes it. | `12. B, callback lost: stays submitting until the next look sees GRANTED` |
| Platform B sends the callback twice, or a late one that contradicts the final state | Only a `submitting` redemption can be finished; later notices change nothing and coins are taken once. | `13. B, callback twice: the second changes nothing, one capture` |
| The platform answers 500 or 429 | The redemption is never refused; it stays `submitting`, the delay grows (1 s, 2 s, 4 s) or follows Retry-After, and it ends issued with one grant. | `14a. A, three 500s and one 429 at grant: stays submitting, honours Retry-After, ends issued with one grant` |
| The platform cannot answer our lookup | We do not issue blind; no grant request is sent until a lookup works. | `14b. A, the look fails: no blind re-issue while we cannot look` |
| We die after the ledger reserve, after the platform accepted, or after the capture | The job runs the step again: the ledger repeats are harmless (fixed ids) and the platform is looked at first; the result equals a clean run. | `15. crash points: the step ran, the process died, the job runs again` (platform A and platform B) |
| The ledger does not answer while settling | The redemption shows `issued` with `settled` false; the next run captures; coins are taken once. | `16. ledger away while settling: shows issued but not settled; settles on the next run; charged once` |
| A reward webhook has a bad signature, comes for platform A, arrives for another tenant's redemption, or arrives too early | 401 plus an audit row; 400; 404 with nothing changed; ignored and recorded. | `17. reward webhook: bad signature, other tenant, platform A, and a notice too early` |
| A player of one tenant reads or redeems in another tenant | 404; the item list shows only the player's own tenant. | `18. tenant isolation on the player API` |
| The request has no token, no Idempotency-Key, or an unknown item | 401, 400, 404, and no redemption is created. | `19. a missing Idempotency-Key is 400, a missing token is 401` |
| The outbox timer and the request both try to run one redemption | Whoever claims the job first runs it; the other finds a live lease and returns without running. Only one request reaches platform B. | `21. the timer and the request never run one redemption at the same time (B has no idempotency)` |
| A worker dies while running a job | Its claim stays until `claimed_until`; then the job is due again and another worker runs it (handlers are safe to repeat). | `outbox > a lease that ran out: the second worker runs the job and the slow first worker is fenced out` |
| A slow worker finishes after its lease was taken over | Its result is not written (the write is fenced by the claim token); `outbox.lease_lost` is logged; the row shows the new worker's outcome. | `outbox > a lease that ran out: ...` |
| A job is enqueued again while a worker runs it | The claim is left alone and `rerun` is set; after the first run the job runs once more, never at the same time. | `outbox > an enqueue while the handler runs leads to exactly one more run, ...` |
| Runs with faults end somewhere else than a clean run | They all end in the same state (status, settled, balance, grant count). | `20. differential: every run with faults ends where the clean run of the same input ends` |
| The judge is blind to a violation | The judge reports a double grant, a missing grant, a negative balance, coins held after settling, a grant for a refused redemption and a grant to the wrong player. | `the judge can say no` (6 tests) |
| TigerBeetle is down when the redemption is created | The request still returns 201 with `created`; the job retries with a growing delay and never dies on this error. | Not tested (the capture case in test 16 covers only the settle step) |
| The process dies between the PostgreSQL commit and the ledger call with a real SIGKILL | The job is due again and repeats the step. | Tested with a real kill: `real processes > B. the API is killed after the request committed and before any job ran ...` (the kill is after the commit and before any job; a kill between two statements of one job is only covered by test 15 and by A, where the kill lands inside a job) |
| Platform B takes a long time to decide | The redemption stays `submitting` for as long as it takes, asked every 2 s; the coins stay reserved and visible. | Not tested for a long wait (only the short paths) |
| Platform B's lookup does not show a request that B accepted a moment ago | We would issue a second grant. This is an assumption written in the contract. | Not tested, cannot be handled from our side |
| A and B outcomes disagree (lookup says GRANTED, a late callback says DECLINED) | The first final answer wins; the later notice is ignored. | Partly: `13. B, callback twice: ...` (late contradicting notice after GRANTED) |
| An operator wants to revoke a reward after it was issued | Not built. The redemption is final once issued. | Not tested (not built) |
| The same pending reserve is captured and also released | The ledger refuses the second one (LedgerConflict) and the job retries and goes dead, visible in the outbox. | Not tested in this file (ledger tests cover the conflict) |

## Processes and the schema

| What goes wrong | What the system does | Proved by |
|---|---|---|
| A process starts (a worker is added, a container restarts) while others are busy | It applies the schema only if the schema text changed (hash in `schema_state`), so it takes no table lock and cannot deadlock with live requests. Before this fix the schema script took exclusive table locks even when nothing changed: the new process died with `deadlock detected` and a redemption request got a 500 (found by `test/processes.test.ts`, 6 runs of 11). A deploy that changes the schema still takes those locks once. | `migrate under load > a schema that is already applied does not wait for a transaction that has written to the tables` |
| A worker is killed (SIGKILL) while it holds claimed jobs and the casino has already granted | The claim stays until the lease ends; another worker takes the job, looks first, finds the grant. Every job ends done, one grant per redemption, coins right. | `real processes > A. a worker is killed while it holds claimed jobs ...` |
| Three workers on one database under load | Every redemption issued once (one `issue` call each), every job done, none dead, no lease lost. | `real processes > C. three workers, 30 spins and 30 redemptions ...` |
| A handler is slower than its lease | The second worker takes the job; the first one's result is not written (`outbox.lease_lost` logged); platform A has one grant each. On platform B this would grant twice: the lease must be longer than the handler. | `real processes > D. a handler that outlives its lease ...` |

## Random faults

Test name is in `test/properties.test.ts`.

| What goes wrong | What the system does | Proved by |
|---|---|---|
| Any mix of faults (error, rate limit, refuse, lost request, lost answer, slow answer on grant and look; lost, twice or delayed callback on B) meets any mix of deposits, repeats, spins and redemptions, on both platforms, with time moving between actions | After the faults stop and the jobs run: no reward twice, every issued redemption has one grant, refused ones none, no negative balance, coins equal prizes minus issued costs, nothing reserved, every redemption final and settled, no dead job. | `property: faults and player actions > the judge finds nothing and every redemption ends final` (60 runs, fixed seed; 150 runs random seed in `npm run test:deep`) |
| A late notice from B contradicts a final redemption | Nothing changes. | Same test (sent at the end of every run) |

## Operations: admin API, manual resolution, alerts

Test names are in `test/admin.test.ts` and `test/alerts.test.ts`.

| What goes wrong | What the system does | Proved by |
|---|---|---|
| Someone calls the admin API without the key, with a wrong key, with another tenant's key, or for an unknown tenant | 401 with the same body each time; nothing is read. | `admin API > 1. auth: ...` |
| A casino accepts a reward and then goes silent (no error anywhere) | The redemption is listed as stuck once it is older than the tenant's limit, with its age and its last platform call; the alert `redemption_pending_too_long` fires on age, not on errors. | `admin API > 3. stuck: ...`, `alerts > redemption_pending_too_long: ...` |
| The outcome cannot be learned at all | An admin resolves it by hand through the same `confirm` as every answer; the admin is the actor in the audit trail with the note; the ledger settles normally. | `admin API > 4. resolve as issued: ...`, `5. resolve as refused: ...` |
| An admin decides "issued" and the casino never granted | Our books say issued, the casino has nothing. The judge reports it. This is the cost of a manual decision, written down in the test. | `admin API > 4. resolve as issued: ...` |
| An admin resolves a redemption that is final, `created`, insufficient, another tenant's, or sends a bad note | 409 with the view, 404, or 400; nothing changes; a second resolve is 409 and writes one record only. | `admin API > 6. not resolvable: ...` |
| The casino's real answer arrives after a manual resolution and disagrees | Status and ledger stay as the admin left them; one `outcome_contradicted` audit row; a critical alert. An answer that agrees writes nothing. | `admin API > 7. a late real answer ...` |
| The casino's answer and an admin's resolution arrive at the same moment | Exactly one makes the redemption final, in either order; the ledger is captured or released, never both; no false contradiction when the admin loses. | `admin API > 8. the real answer and a manual resolution at the same moment ...` (24 runs; both orders occurred in the runs I looked at, not guaranteed) |
| A dead outbox job | Critical alert with the count. | `alerts > outbox_dead_jobs: ...` |
| A dead outbox job is enqueued again (the player repeats the request) | The job is revived with 0 attempts and runs again, on purpose, but a warning `outbox.revived` with the error it died of is logged. | `outbox > enqueueing a dead job again revives it and logs outbox.revived ...` |
| The wheel is changed so that it pays too much | Warning when the expected prize of the newest wheel is above the tenant's limit (exact integer arithmetic). | `alerts > wheel_expected_prize_high: ...` |
| The wheel pays more than its weights say | Warning when at least 200 spins in 24 hours have a mean more than 25 percent above expectation. | `alerts > wheel_paying_above_expectation: ...` |
| A player gets many deposits and spins (the deposit, spin, withdraw loop) | Warning per player above the daily limit. | `alerts > many_spins_one_player: ...` |
| One player takes most of the issued coins | Warning for a player above the share limit, only when the tenant total is large enough. | `alerts > player_redeem_share_high: ...` |
| A tenant has no ops policy | One critical alert `no_ops_policy`; no error. | `alerts > no ops policy: ...` |
| Thresholds differ between operators | They are a versioned policy of the tenant; a new version changes the result, another tenant is not affected. | `alerts` tests with policy version 2 and 3; tenant isolation inside each alert test |
| A deposit is reversed after its spin was used | Not built: the adapters have no reversal event. | Not tested (not built) |
| The alert reaches nobody | Not built: no delivery to us or to the operator; the endpoint is for a scheduler to poll. | Not tested (not built) |
| The daily digest agent misreads or is misled by outside text | It is read-only and told that event text is data. Nothing runs it yet. | Not tested (not built); the playbook SQL runs against the schema: `the monitoring playbook > every sql block ...` |
| A casino's event signing key leaked | The casino's manager (or us) replaces the key with "old key stops working now" (`previousValidForSec` 0). From that moment an event or a result notice signed with the old key gets the same 401 as any bad signature. The new secret is shown once. The casino must paste it into its configuration, and until it does, its real events are rejected too: that is the price of a fast stop. | `tenant-keys > 1a. 0 seconds: the old secret is rejected at once, exactly like a bad signature; the new one works`, `1b. 0 seconds: the old secret fails for a deposit and for a notice; the new one works for both`, `4a. 0 seconds: the old token secret is rejected at once, the new one works` |
| A planned key change | The key is replaced with the old one kept for up to 24 hours. Both work; after the time only the new one. The old one can also be dropped early. | `tenant-keys > 2a. 3600 seconds: both work; after an hour the old one is rejected and the new one works`, `2b ... platform B`, `3a. 3600 seconds, then revoke the previous: the old one is rejected at once; a second revoke is still 200`, `4b`, `4c` |
| Two people replace the same key at once | The tenant row is locked: they run one after the other, both get 201, exactly one secret is current and the other is its previous key. | `tenant-keys > 9. they run one after the other; one secret is current, the other is the previous one` |
| A secret ends up in the audit trail or a log | Masked by name in the audit trail (the `*_prev` columns too) and by key name in the log; the list shows hints only. | `tenant-keys > 8. the list shows hints only; no audit row and no log line holds any secret` |
| A new route forgets the tenant filter, or an old query loses it | Beta's actor calls every route with alpha's identifiers and must get 404 or an answer with none of them; writes must leave alpha's rows unchanged. A route with no decision (a check or a reason) fails the test, so a new route cannot be added without choosing. | `tenant-isolation > every route has a decision, and every list entry is a live route` and one test per checked route (`tenant-isolation > checked routes > GET /admin/:tenantId/redemptions` and the others) |
| The casino reports a deposit as pending, then as completed, under one id (or completed first, then pending) | An ignored event is stored under its id plus its type or state, so it does not take the key of the completed deposit. The completed one is accepted once and gives its spins; the same pending or completed event twice is one row; a late pending after a completed one changes nothing. | `intake > 4b. one id reported as pending and then as completed gives one spin, on both platforms, in any order` |
| The ledger is away for a long time after a spin | The spin is saved as used, with its coins, and the `spin_credit` job asks again later with a growing wait (1 s up to 60 s) for as long as the ledger is away. It never goes dead for this reason. When the ledger returns the prize is credited once. | `wheel > 7b. a long ledger outage never kills the spin_credit job; the prize is credited once when the ledger returns` |
| A player or a casino sends an id made of 36 hyphens as a redemption or item id | The id check is the strict UUID form (one shared check, `src/domain/uuid.ts`), so the answer is 404 and not a database error. | `store > 16b. an id of 36 hyphens is not a redemption or an item: 404 or 400, never 500` |
| A platform B redemption stays pending for a long time (the callback never comes) | The job looks again with a growing wait (2 s, 2 s, 4 s, ... up to 60 s) and writes a `platform_call` audit row only when what it saw changed from the last look, so an hour of waiting is about 60 looks and a handful of rows. | `store > 12b. B, a stuck redemption: over one hour the look-ups are bounded and the audit rows do not grow per look` |
